2. Key Architecture Decision — Standalone Service

The admin backend is a separate, standalone service: vidyouth-admin-backend/, a sibling of vidyouth-login-backend/. It is not nested inside the login API.

ConcernDecision
Process / deployIndependent service, its own package.json, its own port (default 8090; 8091 locally)
DatabaseShares the platform Postgres — reads users/sessions/audit_events, owns feature_flags
SessionsShares platform Redis — honours force-logout via the same sess:{userId} set
TokensVerifies the same RS256 access tokens the login API issues — public key only, never signs
Login API impactZero — the login backend was reverted clean; it contains no admin code

Why: independent blast radius, deploy cadence, and scaling for the admin panel; the login API stays minimal and unchanged. The trade-off is a small amount of duplicated infrastructure code (DB pool, JWT verify, audit writer), which is intentional for service isolation.

4. Code Walkthrough — Every File

config/env.ts

Zod-validated environment, crashes loudly at boot if misconfigured. Declares PORT (default 8090), DATABASE_URL, REDIS_URL, JWT_PUBLIC_KEY, JWT_ISSUER, JWT_AUDIENCE. Deliberately has no JWT private key — the admin service never signs tokens.

db/pg.ts & db/redis.ts

pg.ts — a small Postgres pool against the shared platform DB (query(), pingDb()). redis.ts — ioredis client against shared Redis; exposes isSessionActive(userId, sessionId) which checks the sess:{userId} ZSET. This is what makes force-logout (PRD FR-AUTH-003: "Super Admin can remotely invalidate all sessions") also lock the admin panel — a revoked token cannot reach /admin/*.

services/jwt.ts

verifyAccess(token) only. Verifies RS256 signature, issuer, audience, and that the token kind is access. Uses the login API's public key, so admin and login share one identity system with no duplication of credentials.

services/permissions.ts — the RBAC source of truth

Implements the PRD §16.1 permission matrix as a per-role permission set. can(role, permission), permissionsFor(role), assertCan(). Per the PRD only superadmin holds access_admin_panel; Org Admin explicitly does not.

Permission (PRD §16.1 / §7.6)superadminadmin (Org)organisationvendorstudent (B2C)
access_admin_panelYesNoNoNoNo
manage_all_usersYesOwn orgNoNoNo
view_any_user_dataYesOwn orgOwn orgNoNo
create_edit_content / configure_pricing / payments / certificates / orgs / vendors / news / audit logsYesNoNoNoNo
access_vendor_portal / mark_offline_attendanceNoNoNoYesNo
apply_to_jobs / build_resumeNoNoNoNoYes

PRD role names map to system roles: SUPER_ADMIN→superadmin, Org Admin→admin, ORG_USER→organisation, VENDOR→vendor, B2C_USER→student. (MENTOR is PRD V1.5, not in the enum yet.)

middleware/auth.ts & middleware/rbac.ts

auth.ts — extracts the Bearer token, verifyAccess(), then isSessionActive(); attaches req.user. rbac.ts — requirePermission(p) / requireAdminPanel run after auth and return 403 if the role lacks the permission, recording an admin.access.denied audit event. This is the "service level" half of the PRD rule: "RBAC enforced at API gateway AND service level — never client-side only."

repositories/feature-flags.ts

List / get / set the feature toggles. Writes record updated_by + updated_at for accountability.

routes/admin.ts — the endpoints

Every route is gated [app.auth, requireAdminPanel] (valid non-revoked session → superadmin only). See the endpoint table in §6.

routes/health.ts & server.ts

health.ts — /livez (process up), /healthz (db + cache reachable). server.ts — Fastify bootstrap with helmet, CORS, rate-limit (100/min), the auth decorator, graceful shutdown, and a test-mode guard so the suite drives it via app.inject().

5. Security Model — Request Authorization Chain

Bearer token
   │
   ▼  middleware/auth.ts
1. signature + issuer + audience + kind=access   (services/jwt.ts, RS256 public key)
2. session still active in shared Redis            (db/redis.ts isSessionActive)
   │  ── fail → 401 (missing_token / invalid_token / session_revoked)
   ▼  middleware/rbac.ts
3. role has 'access_admin_panel'                   (services/permissions.ts §16.1)
   │  ── fail → 403 forbidden  + audit 'admin.access.denied'
   ▼
4. route handler runs (routes/admin.ts)            + audit 'admin.access'

Authorization is decided entirely server-side from the verified token's role — nothing the client sends influences access.

11. How to Run It (for the team)

# prerequisites: the shared platform Postgres + Redis must be up
cd vidyouth-admin-backend/app
npm install
# app/.env must provide: DATABASE_URL, REDIS_URL, JWT_PUBLIC_KEY,
#   JWT_ISSUER, JWT_AUDIENCE  (point at the same Postgres/Redis the
#   login API uses; JWT_PUBLIC_KEY = the login API's public key)

# one-time, against the shared DB, AFTER the login API migrations:
psql "$DATABASE_URL" -f ../database/migrations/001_feature_flags.sql

npm run dev      # http://localhost:8090  (8091 locally if 8090 is taken)
npm test         # 15/15
npm run build    # tsc → dist/  (deployable artifact)

The service verifies tokens the login API issues — a user logs in via the login API (8080), receives a JWT; if their role is superadmin that same token is accepted by the admin API.
